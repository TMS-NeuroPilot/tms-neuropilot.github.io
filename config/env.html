.env reference#

.env lives in the repository root and is read once, at import, before any component starts. It is the bootstrap and override layer: a key here wins over the lab profile and over the built-in defaults.

Create it once:

bash
cp .env.example .env

Syntax#

.env follows python-dotenv:

bash
RELAY_HOST=127.0.0.1
ROOT_FOLDER=/data/neuropilot        # comments after a value
EMG_COMPUTER_PASSWORD="p a s s # 1" # quotes protect spaces and '#'

Rules the Config tab's writer follows so a round-trip is lossless:

  • a value containing spaces, #, quotes or backslashes is written quoted;
  • inside double quotes, backslashes and quotes are escaped;
  • unquoted values are trimmed;
  • comments and unknown keys are preserved when the GUI writes the file.

⚠Values are read at import

Editing .env while the controller runs changes nothing until restart. This is the most common "my change did nothing" report.

Required vs optional#

Every key has a default in the code, so a missing .env starts the suite with the documented values. A checkout without any .env at all is still a bad idea: the analysis keys are read at import, and the defaults are the example protocol, not yours.

Precedence reminder#

text
shell environment  >  .env  >  lab.yaml  >  defaults

A key exported in the shell beats .env; a key in .env beats the GUI's Lab page. See Settings model.
